# 0.6.0 — CLI-injected workflow enforcement and skill folder rename

## TL;DR

Four changes ship together:

1. **CLI-injected workflow enforcement.** The "Protocol Discovery for This Step" responsibility moves off the agent and onto the CLI. At `init` / `repair` time the CLI reads `.stackshift/installed.json`, resolves the active protocol set, and rewrites the materialized workflow files and `SKILL.md` so they list only the protocols the user actually installed.
2. **Skill folder rename: `stackshift-core` → `stackshift`.** The `-core` suffix was only meaningful while sibling tier-bundle skill folders existed. Those were removed in 0.3.0 and the seed stub was removed in 0.5.1 — there is only one skill folder now.
3. **Skill folder is pruned to the installed set.** `init` and `repair` trim the destination `skills/stackshift/protocols/` and `seeds/` so they contain only the entries recorded in `installed.json`. Required-tier protocols are always part of every install; recommended / optional / custom only land if the user picked them. The in-skill `_registry.json` and `seeds/_registry.json` are rewritten to match. `_step-map.json`, `_template/`, and any other non-protocol files are preserved untouched. The shipped repo `skills/stackshift/` remains the full catalog.
4. **Repair upgrades pre-0.6.0 installs.** `init` and `repair` detect any legacy `stackshift-core/` folder at the install path, remove it, re-copy `stackshift/` from the shipped skill source, and re-inject markers. Same idempotent purge pattern used in 0.3.0 (tier bundles) and 0.5.1 (seed stub).

## Why

The agent's per-step protocol discovery instructions consumed ~600–900 tokens per workflow turn and relied on the model honoring "if installed, then enforce" branching. Weaker models would skip the check or get the tier semantics wrong. Now the only thing the agent reads is a pre-resolved list of protocols that actually apply — no `installed.json` reads at every step, no tier logic, no skipping protocols the user did install.

## What changed

### Canonical workflow files now contain marker regions

Each of `workflow/1-schema-fields.md`, `workflow/2-section-schema.md`, `workflow/3-types.md`, `workflow/4-variants.md`, and `workflow/5-groq.md` gains a single CLI-owned region:

```markdown
<!-- CLI:PROTOCOLS:BEGIN step=N -->
> The CLI injects this block at install. Do not edit by hand —
> it will be overwritten by the next `init` or `repair`.
<!-- CLI:PROTOCOLS:END -->
```

The previous "Protocol Discovery for This Step" prose was deleted. The CLI replaces the marker block with a flat, pre-resolved Required / Recommended / Optional list, grouped by tier. If a tier has zero installed protocols for that step, the sub-heading is omitted. If all protocols for the step are absent, the block becomes `_No protocols active for this step in the current install._`.

### Step 2 also has a `CLI:SEED` region

Replaces the old "Seed gate" prose. When a seed is installed, the CLI inlines the strategy id and a hard rule that no `initialValue/` file may be written before loading the strategy doc. When no seed is installed, the block becomes an explicit "do NOT write any `initialValue/` files" rule — stricter than the prior "proceed without one" wording.

### `SKILL.md` cross-cutting table is pruned at install

The keyword-routing table for cross-cutting optional protocols (`auto-verify-hook`, `auto-validate-hook`, `modal-sheet`) is wrapped in `CLI:CROSSCUT` markers. The CLI only writes rows for protocols whose id is in `installed.json` `protocols[]`. The "Stage 1 / Stage 2" prose was collapsed to a single short paragraph; keywords still drive matching, but stale rows for uninstalled protocols no longer mislead the agent.

### `_step-map.json` declares per-step protocol membership

New file: `skills/stackshift/protocols/_step-map.json`. Lists which protocols belong to which step, and which are cross-cutting. The CLI intersects this map with `installed.json.protocols[]` to produce each step's injected block. Adding a protocol to a step is now a one-line edit to this JSON — no workflow-file edit needed.

### `injectWorkflowProtocols()` in `cli/src/writer.ts`

Walks the materialized skill folder, rewrites the marker regions in `SKILL.md`, `workflow/1-schema-fields.md`, `workflow/2-section-schema.md`, `workflow/3-types.md`, `workflow/4-variants.md`, and `workflow/5-groq.md`. Idempotent — second run produces the same output. Wired into `writeSelection` (init) and into `repair`. The implementation is platform-agnostic: it mutates files inside the CLI-owned `.agents/skills/stackshift/` (or platform equivalent) folder only, so it works identically for every agentic platform the CLI supports.

### Skill folder rename

`skills/stackshift-core/` → `skills/stackshift/`. The `name:` field in `SKILL.md` frontmatter is updated. Every CLI path that referenced `stackshift-core` is updated. Install destinations (`.agents/skills/stackshift-core/`) become `.agents/skills/stackshift/`.

### Skill folder is now pruned to the installed set

The shipped `skills/stackshift/` tree is the full catalog of every registered protocol and seed. Each install destination — `.agents/skills/stackshift/` (or platform equivalent) — is pruned to the subset recorded in `.stackshift/installed.json` so the agent never reads files for protocols the user did not install. Required-tier protocols are part of every install, so they are always kept; recommended / optional protocols only land in the destination if the chosen tier (or a custom selection) included them. The in-skill `protocols/_registry.json` is rewritten to match. The `seeds/` folder is treated the same way against `installed.json.seed`: when no seed is selected, every seed file is removed and the registry's `seeds` array is emptied.

`_step-map.json`, `_template/`, and any other non-protocol entries inside `protocols/` are not touched. The prune is idempotent — re-running `init` or `repair` reproduces the same destination state.

### Legacy purge

`removeLegacyBundleFolders` in `cli/src/writer.ts` and `purgeLegacyBundles` in `cli/src/repair.ts` now include `stackshift-core` in `LEGACY_BUNDLE_NAMES`. The lock-entry filter strips any `stackshift-core` entry from `skills-lock.json`. Repair gains an `ensureStackshiftCopied()` step that re-copies the new skill folder from the shipped source when only the legacy folder existed before the purge.

## Migration for existing installs

Automatic. The next `npx @extragraj/stackshift-skills init` or `repair`:

1. Removes any `stackshift-core/` folder at the install path and strips matching `skills-lock.json` entries.
2. Re-copies the new `stackshift/` folder from the shipped skill source.
3. Prunes the freshly copied `stackshift/protocols/` and `seeds/` down to whatever is recorded in `.stackshift/installed.json` (any protocol files for ids no longer in the marker disappear; required-tier files are always kept).
4. Re-injects the CLI:PROTOCOLS / CLI:SEED / CLI:CROSSCUT markers from `.stackshift/installed.json`.

No data migration is required. `.stackshift/installed.json` itself is untouched — its schema did not change. The first reinstall after upgrade simply updates `skillVersion` to `0.6.0`. Upgrading tier (e.g. required → full) re-adds the missing protocol files on the next install; downgrading removes them again on the install after that.

## Caveat

If a user hand-edits `.stackshift/installed.json` to add or remove a protocol without re-running `init` / `repair`, the workflow files go stale until repair. Documented in CLAUDE.md and the CLI help — re-run `repair` to refresh.

## Testing

Verified end-to-end across four temp installs (`temp/required`, `temp/recommended`, `temp/full`, `temp/custom`) plus a legacy-upgrade simulation (`temp/legacy-upgrade`):

- Required tier — Step 1 lists only the two required protocols; Step 4 lists only `variant-router`; cross-cutting block is empty. `.agents/skills/stackshift/protocols/` contains exactly the four required `.md` files plus `_registry.json` (trimmed to those four), `_step-map.json`, and `_template/`. `seeds/` contains only `_registry.json` with an empty `seeds` array.
- Recommended tier — Step 1 adds the four recommended protocols. Skill destination contains the 4 required + 7 recommended `.md` files. `_registry.json` matches.
- Full tier — Step 4 includes Required / Recommended / Optional groups; cross-cutting block has all three rows. Skill destination contains every registered protocol; `_registry.json` is the full list.
- Custom tier — handcrafted `installed.json` subset (4 required + 1 recommended + 2 optional, plus `seed: initialvalue-seeding`) re-injected via `repair`. Markers reflect exactly that subset. Skill destination's `protocols/` contains exactly those 7 entries (and `modal-sheet/` as a directory); `_registry.json` contains only their entries; `seeds/initialValue-seeding.md` is present and `seeds/_registry.json` lists only the one active strategy.
- Tier upgrade / downgrade — re-running `init --tier full` over a required install re-adds the missing protocol files; re-running `init --tier required` over a full install trims them back. Both are idempotent on re-run.
- Legacy upgrade — `stackshift-core/` removed, `stackshift/` re-copied, pruned, and markers rewritten, all in one `repair` invocation.

`validate` and the idempotent reinstall path continue to pass.

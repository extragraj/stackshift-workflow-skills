# 0.5.0 — Static protocol enforcement (`validate` + auto-validate-hook)

## What changed

Protocol enforcement is no longer purely prose. The CLI ships a static linter that reads `.stackshift/installed.json`, enumerates the active protocols, and applies per-protocol checks against `schemas/custom/**/*.ts` and `components/sections/**/index.tsx`. A new optional protocol wires the linter as a Claude Code `PostToolUse` hook so violations surface inline on every Write/Edit.

This closes the gap documented in `ANALYSIS.md` Section 3 — "outside of Step 4 and only when UI Forge happens to be present, there is no hard enforcement". Steps 1, 2, 3, and 4 now have validator-driven enforcement for the protocols that have statically checkable invariants.

### Added

- **`cli/src/validate.ts`** — new CLI command `validate`:
  - `npx @extragraj/stackshift-skills validate` lints the whole project.
  - `npx @extragraj/stackshift-skills validate --file <path>` lints a single file (used by the PostToolUse hook).
  - `--json` emits a machine-readable findings array for CI.
  - Exits **1** on `required`-tier findings, **0** otherwise. `recommended`-tier findings print as `warn` lines.
  - Reads `.stackshift/installed.json` to enumerate active protocols. Protocols not in the marker are skipped — adding a new protocol does not retroactively flag existing files unless the user opts in.

- **`auto-validate-hook` protocol** (optional tier) — bootstrap merges a `PostToolUse` entry into `.claude/settings.json`:
  ```json
  { "matcher": "Write|Edit",
    "hooks": [{ "type": "command",
                "command": "npx -y @extragraj/stackshift-skills validate --file \"$CLAUDE_FILE_PATH\"" }] }
  ```
  Idempotent — re-running bootstrap detects the existing StackShift validate entry (by command substring) and replaces it. Independent of `auto-verify-hook`; both can coexist.

- **Per-protocol static checks** — initial coverage:

  | Protocol | Tier | Check |
  |---|---|---|
  | `factory-function-pattern` | required | No `defineField(` / `defineType(` calls in `schemas/custom/**/common/fields.ts`. |
  | `sub-field-visibility` | required | No duplicate `name: '...'` entries within a single section schema file. |
  | `variant-router` | required | Exported `<Name>Props` interface, `?? undefined` (not `?? null`), `if (!Variant) return null;`, `{ data }: SectionsProps` signature. |
  | `preview-conventions` | recommended | Every `type: 'array'` / `type: 'object'` block has a `preview:` key. |

  Checks are regex-based, intentionally conservative — they flag only patterns that are unambiguously wrong. AST-based checks can replace them later without changing the CLI surface or the marker schema.

### Modified

- **`cli/src/index.ts`** — new `validate` subcommand routes to `runValidateCli`. Root `--help` only triggers when no subcommand is supplied so `validate --help` reaches the validator's own help text.
- **`cli/src/flags.ts`** — help output documents the new command and shows example `validate` invocations (single file, JSON).
- **`cli/src/writer.ts`** — new `tryInstallAutoValidateHook()` mirrors the existing `tryInstallPostToolUseHook` pattern for `auto-verify-hook`. The new hook runs even when UI Forge is not detected (it's StackShift-internal). `UiForgeIntegrationResult` gains an `autoValidateHookInstalled` flag for the install summary.
- **`cli/src/install.ts`** — summary block surfaces both hook installations independently.
- **Workflow files** — each step's "Done when" gains a single new item:
  - `workflow/1-schema-fields.md`, `workflow/2-section-schema.md`, `workflow/3-types.md`, `workflow/4-variants.md` — add `Validate: npx @extragraj/stackshift-skills validate --file <output>` as a postcondition. Step 5 (`pages/api/query.ts`) is not in scope for the validator, so its checklist is unchanged.
- **`SKILL.md` Section 3** — `auto-validate-hook` joins the cross-cutting protocol keyword table alongside `auto-verify-hook` and `modal-sheet`.
- **`README.md`** — new `Validate` subsection under Installation; new row in the Protocols table; Protocol System paragraph cross-references the static enforcement path.
- **`CLAUDE.md`** — Commands block mentions `validate`; CLI Architecture lists `validate.ts`; Bootstrap Flow describes the hook merge for both `auto-verify-hook` and `auto-validate-hook`; Extending block reminds maintainers to add a validator check when shipping a new protocol with a statically checkable invariant.

## Bugs fixed

**Protocol enforcement was "advisory only" outside Step 4.** Per `ANALYSIS.md` Section 3, Steps 1, 2, 3, and 5 relied 100% on prose instruction-following. On Open Router models and lower-tier endpoints, compliance dropped without any signal. There was no test that failed because `factory-function-pattern` was ignored — the author only noticed when reviewing the PR. Fix: ship a static linter, wire it as a PostToolUse hook so violations show up inline before the agent moves on, and add a per-step "Validate" postcondition so manual invocation is documented for non-Claude-Code runtimes.

## Migration for existing installs

The new protocol is optional and unchecked by default. Existing installs are unaffected until the user opts in by re-running `init` and selecting `auto-validate-hook` (or by editing `.stackshift/protocols/_registry.json` manually). On the next `init` or `repair`, the CLI overwrites the materialized skill folder so the new protocol doc, workflow updates, and reference content land automatically.

The `validate` command works on any existing install — no protocol opt-in required. Running it returns findings against whatever protocols are already in `.stackshift/installed.json`.

## Token cost impact

The validator runs as a subprocess outside the agent's context window. The PostToolUse hook reports findings to the agent via stderr only when they exist — clean writes produce no agent-side context. Compared to the pre-0.5.0 prose-only enforcement, agents on cold-start turns no longer need to scan and apply protocol invariants from memory: the hook does it deterministically and surfaces only the diff. Expected impact: −1k to −3k tokens per cold turn on schema-heavy work, and significantly lower variance in compliance across model tiers.
